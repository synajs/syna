# Changelog

## 1.0.0-rc.4

The cleanup phase, from a three-party cross-review of 1.0.0-rc.3 (`9c57269`): six items, five of them reproduced by at least two reviewers in environments rebuilt from the lockfile. Task book `work/tasks/SYNA_RC4_EXECUTION_PROMPT.md`; root-cause report `work/rc4/ROOT_CAUSE.md`; baseline, probes and the pre-fix reading of every new test in `work/rc4/BASELINE.md`; the semantic record is `docs/SEMANTIC_CHANGES_RC4.md`. **The public API inventory is identical to the 1.0.0-rc.3 record item by item** — 0 added, 0 removed, 0 changed, 0 doc-only. The planning layer (`entry-planner`, `graph-builder`, `definition-compiler`, `plan-cache`) is untouched and the reference planner differential and the explain/inspect snapshots are unchanged. `docs/SEMANTIC_MODEL.md` §11 and §13 are clarified, not revised.

- **The close set is closed before any abort listener runs, and a close is entered before it begins** (N2, N3). `AbortController.abort()` executes its listeners synchronously and the stop signal is the cancellation path handed to every `setup()`, so both halves mattered. `dispose()` was `this.disposePromise ??= this.runtime.disposeEnv(this)`, and `??=` assigns after the right-hand side is evaluated: a listener that re-entered `dispose()` found no Promise there and started a second close, the two raced for the same slots, the one that arrived second completed empty-handed and announced `disposed` — and a cleanup that threw could end up in whichever of the two nobody awaited, lost rather than late. `broadcastClosing()` marked and aborted in one depth-first pass, so a listener saw descendants that were still `ready`: it could start a dormant Service inside the very set being closed (`setup()` really ran, acquiring what it acquires, before the instance was discarded as a late result) and could add a whole grace period to a close whose bound is computed from the tree as it stood when the close began. Both closes are now entered — synchronously, before the broadcast, so no window opens in which a closing Env still accepts work — and a `dispose()` that arrives from inside one joins it and settles with it; the broadcast marks the whole close set before aborting any of it, `runtime.dispose()` in one pass over every root. A listener that now enters an already-marked child is refused at planning time with `ENV_CLOSED` instead of `ENTRY_ACTIVATION_FAILED`.
- **A cleanup phase reports what it has already determined** (N1). `runCleanups()` collected its failures in a local array and returned only when the whole phase had ended, so a failure that was already determined disappeared behind a later cleanup of the same phase that hung — for ever, if it never ended. Each cleanup's outcome is now recorded the moment that cleanup ends; when the close stops waiting for the phase, the failures determined so far are still failures the close waited for and enter the `AggregateError` of `dispose()`, and the late report lists what failed after that point and nothing else. The same treatment at all four call sites: the cleanup of a Ready slot, the rollback of a failed attempt, the rollback of a late result a close discards, and the late close of an abandoned attempt.
- **Nothing suspended on a cleanup keeps a closed Env alive** (N4, an implementation correction like rc.3's L3). An `async` frame suspended on a cleanup keeps its whole register file, `slot` and `owner` included, whether or not the code after the `await` still mentions them — and `slot.ownerEnv` is the Env, its plan, its Input payloads and its sibling slots. Two of the four paths that can outlive a close still did this: the rollback of a failed setup and the late close of an attempt that settled after the close. The setup sequence is now driven by reactions rather than by one `await` loop, the cleanup phase is a task that holds the cleanups, the identity strings and — from the moment the close stops waiting — only weak handles on the slot and the owner, and a completed close clears `slot.ownerEnv` so that nothing outliving it reaches the Env at all.
- **A waiter is bounded until the current attempt ends, not until its setup Promise settles** (N5). An attempt is over when its `setup()` has settled *and* the cleanup phase that settlement started has ended. Deadlines were cleared at the settlement of the raw Promise and were not armed for waiters joining afterwards, so a setup that failed at 10 ms with an `onDispose` that hung left every `load()` pending for ever — no `LOAD_TIMEOUT`, no event, the slot stuck in `starting` — on an Env that was never closed, and left `enter()` pending for an eager slot. Every waiter is now bounded to the end of the attempt; a wait ended during a rollback ends only that wait, the attempt is not overdue, nothing is listed and the cleanups keep running. No new limit and no global rollback timeout: an unfinished rollback still starts no overlapping attempt, a rollback that succeeds leaves the retry rules of the sequence untouched, and one that fails still yields the `AggregateError` of setup and cleanup followed by `ROLLBACK_FAILED`.
- **The reference application's acquire deadline covers the site creation** (A4). `acquireTimeoutMs` stopped at the door of `create()`: the three awaits inside it and the wait on somebody else's `record.creation` had no deadline and no signal, so a 20 ms timeout could return a working lease 85 ms later and a caller stuck in a creation only learned of a `shutdown()` when the creation returned. One deadline now covers the whole acquire, as `docs/MULTITENANT_BLOG.md` has promised: what is bounded is the *caller's wait*, never the creation, which keeps running, keeps its Env and stays available to everyone else. The first caller's timeout does not fail the second, and it is not counted against the tenant. No new setting and no new error code.
- **The gate's timing assertions** (G1). `close-matrix.test.mjs` compared a measured duration against a budget with no tolerance, and a cloud run went PARTIAL at 39 ms against 40 ms (libuv may fire a timer a fraction early and `Date.now()` truncates both readings). The claim is now two tests: a deterministic one that intercepts timer construction and asserts budget attribution and arming order with no reading of elapsed time, and a wall-clock one that keeps its upper bound and takes its lower bound from a monotonic clock with a stated 5 ms slack. No test asserts concurrency or seriality from an exact number of timers.
- **A property test over random graphs** joins the gate (`packages/core/tests/rc4-graph-property.test.mjs`): 200 shapes on a fixed seed — edges, cycles, never-materialized intermediate nodes, several cleanups per slot, success and failure combinations — checked against a reachability oracle computed in the test itself rather than against the Runtime's own condensation, in about 90 ms. Cleanups that hang stay out of it on purpose: they cost a real grace period and would make the gate timing-sensitive.

## 1.0.0-rc.3

The closing paths, from an independent audit of 1.0.0-rc.2 (`d7a4410`): six groups of defects reproduced on that release, all of them on the way out of an Env. Task book `work/tasks/SYNA_RC3_EXECUTION_PROMPT.md`; baseline, minimal increment and the strong-reference inventory in `work/rc3/BASELINE.md`; the semantic record is `docs/SEMANTIC_CHANGES_RC3.md`. The planning layer (`entry-planner`, `graph-builder`, `definition-compiler`, `plan-cache`) is untouched, the reference planner differential and the explain/inspect snapshots are unchanged, and no existing test was rewritten or withdrawn.

- **The cleanup of a Ready slot joins the bounded close** (L1). It was awaited without any bound, so one `onDispose()` that never settles stopped the whole close — the Env stayed `disposing` for ever and its parent with it. Each slot's cleanup phase now has a budget of `limits.disposalGraceMs` of its own; what outlives it is abandoned: the slot is `abandoned`, the ledger lists it under the attempt that produced the instance, and `attempt-abandoned` reports it with the new phase `'cleanup'` and the dependencies it may still be using. The rest of the slots are disposed regardless, that cleanup's dependencies included. Independent components of the SCC condensation are destroyed concurrently while every dependency chain keeps its dependant-first order, so the step costs one budget per slot of the longest chain instead of one per slot. `dispose()` does not reject for an abandoned cleanup; when it ends late the entry leaves the ledger and a failure is reported by `attempt-failed-late`. `runtime.dispose()` gives it the same grace as a settling attempt and reports what is left as `runtime-attempts-outstanding`. **What is bounded is the waiting, not the release of resources** (`docs/SEMANTIC_MODEL.md` §13): an abandoned cleanup keeps running and keeps holding what it holds.
- **Every cleanup failure the close waited for is reported exactly once** (L2). The rollback of an attempt that settled inside the grace — its result discarded by the close — raised its errors into the sequence, which the close only ever observed as "settled"; and the two late events were emitted only for attempts that had gone overdue, so with the waiter cancelled or timed out the failure was visible nowhere. Such a failure now enters the `AggregateError` of `dispose()` exactly once (`error.suppressed` for `run()`), in the existing shape, next to the per-service errors of the Ready slots the close disposed; `attempt-succeeded-late` / `attempt-failed-late` are reported for every settlement from the start of the close, not only after it ended. Waiters are untouched — the same `AggregateError`, `LOAD_CANCELLED`, `LOAD_TIMEOUT` — and what the waiter got never decides whether the close reports. What the close stopped waiting for reports through an event instead.
- **An outstanding attempt no longer reaches its Env's graph** (L3, an implementation correction). Through `attempt.slot.ownerEnv` the ledger, the `FinalizationRegistry`'s held value and the late-settlement closures kept the closed Env, its plan, its Input payloads and its sibling slots alive for as long as the user's setup Promise was pending. A listed attempt now holds its slot only weakly and its owner as a minimal record — id, close flag, the close's cleanup errors, and deliberately not the `AbortSignal`, whose abort reason retains the receiver of every frame of its stack. The late-settlement reactions and the lifecycle handed to `setup()` are built in scopes of their own. A closed Env whose handle was dropped is collectable while its attempt is still pending, and the attempt still runs its cleanups afterwards.
- **The reference application's site manager** (A1, A2/A3): the owner's stop signal set the same flag the shutdown used as its "already done" marker, so on the path where only the Runtime is disposed the wind-down was skipped — the sweep interval kept firing after the manager was gone and queued acquirers were left to their own timeout. Admission (`admissionClosed`) and wind-down (one `shutdownPromise`, awaited by `onDispose` and by every explicit call) are now two things. `acquireTimeoutMs` covers the configuration read as `docs/MULTITENANT_BLOG.md` has promised since 0.5: a caller waits for the shared round-trip only for what is left of its deadline, the round-trip itself is not cancelled, and `shutdown()` ends every in-flight caller's wait with `SITE_MANAGER_CLOSED` without waiting for the store. `stats()` gains `inFlightConfigReads` and `inFlightAcquires`; `pendingAcquires` keeps its meaning, the capacity queue.
- **Documents**: `docs/SEMANTIC_MODEL.md` §11 (the slot states) and §13 (the whole close) revised; `docs/SEMANTIC_CHANGES_RC3.md` new; `docs/API_REFERENCE.md` — the 0.6 comment on `env.state` that contradicted `:197` and §13 is gone, and the close, the event and the lifecycle notes say what now happens; `docs/MULTITENANT_BLOG.md` for the manager; `docs/API_STABILITY.md` registers the exception; `docs/HISTORY.md` records that this round came from an independent audit.
- **Public surface**: `attempt-abandoned.phase` gains `'cleanup'`. The `api-inventory` diff against the 1.0.0-rc.2 record is 0 added, 0 removed, 3 changed (the two others are doc lines of `RuntimeLimits.disposalGraceMs` and `UnsettledAttemptInspection.state`), asserted by the release gate.
- **Tests**: `packages/core/tests/rc3-close-paths.test.mjs` (RC2-L1, RC2-L2, RC2-L2b, RC2-L3 — the audit's core probes flipped), `packages/core/tests/close-matrix.test.mjs` (the 4×4 close matrix, the chain order under concurrent destruction and the time bound of one level) and `apps/multitenant-blog/tests/rc3-close-paths.test.mjs` (RC2-A1 on all three closing paths, RC2-A2, RC2-A3, also a gate step `blog-close-path-tests`).

Semantics (§2.4 — the two revisions the task book mandates; everything else is verbatim 0.6; `docs/SEMANTIC_MODEL.md` §11 / §13, `docs/MIGRATION_V06_TO_V07.md` §4):

- S1 `setupDeadlineMs` is the waiter's timeout, not the attempt's deadline (default still 30_000). It bounds one `load()` wait on the current attempt (re-armed when a retry starts a new attempt); at expiry that wait rejects with `INITIALIZATION_TIMEOUT` (`details.attemptStillRunning: true`, `note` reworded), the slot stays `starting` (`env.inspect()` reports `overdueMs`), the ledger lists the attempt as `timed-out` and `attempt-overdue` (new `RuntimeEvent`) is reported once per attempt. The attempt keeps running: later `load()`s join it with their own windows; a late success is adopted while the owner Env is `ready` (slot `ready`, no cleanup, `late-setup-result` with the new field `adopted: true`) and discarded only by a close (`adopted: false`, cleanups run); a late failure follows the failure policy (`late-setup-failure`). A timeout consumes no `failure.attempts` and triggers no `delayMs`. `enter()` is the waiter of each eager attempt (`ENTRY_ACTIVATION_FAILED` with `causeCode: 'INITIALIZATION_TIMEOUT'`; the rollback close discards the late result). No new option: `load({ signal: AbortSignal.timeout(ms) })` is the shorter wait. Withdrawn 0.6 assertions are registered in `docs/SEMANTIC_CHANGES_V07.md` §撤回. Tests: `packages/core/tests/v07-s1-waiter-deadline.test.mjs`.
- S2 `env.state` is advanced only by Runtime actions (`activating → ready → disposing → disposed`) and is `'disposed'` at the end of the bounded close whatever is still outstanding; no late settlement or garbage collection changes it afterwards, and no test asserts a state through `--expose-gc`. What outlives the close is accounted for in the ledger, decoupled from the state: `runtime.inspect().unsettledAttempts` and the new `env.inspect().abandonedAttempts` (the entries of the slots that Env owns); an entry leaves when the attempt settles (discarded, cleaned up, `late-setup-*`) or its Promise is found unreachable (`attempt-unreachable`; the `FinalizationRegistry` only shrinks the ledger). `dispose()` no longer rejects because user code ignored cancellation: `env.dispose()` / `runtime.dispose()` reject only for a cleanup that threw (the `AggregateError` without a coded member), `attempt-abandoned` carries the new `dependencies` list (the 0.6 report's), `runtime.dispose()` reports a non-empty ledger once as the new `RuntimeEvent` `attempts-outstanding { attempts }`, and `run()` returns the callback's result when the close only abandoned an attempt (`result` on a close error stays for cleanup failures). `UNSETTLED_ATTEMPT` has no throw site left (a running attempt is joined, not refused; the recovery-path guard is an internal invariant) and is removed from `SynaErrorCode` (`docs/MIGRATION_V06_TO_V07.md` §3). Hyla-mini: `onDisposalError` is not called for an abandoned attempt; `close().errors` holds cleanup errors only. Tests: `packages/core/tests/v07-s2-state-and-ledger.test.mjs`; the `--expose-gc` cases keep only ledger / event assertions.

Diagnostics (§2.3 — trigger conditions and messages unchanged; codes and `details` sharpened; `docs/MIGRATION_V06_TO_V07.md` §3 has the mapping tables):

- S6 `FRESH_CONSTRAINT_FAILED` is split by throw site and leaves `SynaErrorCode`: `INACTIVE_REUSE_TARGET` (`{ constraint: 'fresh' | 'share', env, revision | family }`) for a `fresh`/`share` target that is not active in the parent world, `INVALID_INHERITED_CHOICE` (`{ site, selectedKey, candidates }`) for an inherited resolution that is no longer among a site's candidates, `FOREIGN_CANDIDATE_REF` (`{ expectedSourceSlot, receivedSourceSlot }`) for a `CandidateRef` of another collection. `SHARE_CONSTRAINT_FAILED`, backtracking and `check()` / `explain()` reporting are unchanged.
- S7 `INVALID_ENV_STATE` is split by meaning and leaves `SynaErrorCode`: `ENV_CLOSED` (`{ env, state }` | `{ env, state, slot, revision }`) for every operation a closing or closed Env refuses (`enter` / `run` / `check` / `explain` / `derive` from it, an anchored Entry whose anchor is gone, an activation cut short by a close, and a load / retry / recovery under a closing owner), `RUNTIME_CLOSED` (`{}`) for a disposed Runtime, `SLOT_NOT_LOADABLE` (`{ slot, revision, state }`) for `load()` on a disposing / disposed / abandoned slot, `LIFECYCLE_MISUSE` (`{ slot, revision, attempt, state }`) for a stale `onDispose()`. The four sites no caller can reach are internal invariants without a public code. `INVALID_DESCRIPTOR` keeps its code and gets one `details` shape at all 28 sites, `{ descriptor, problem, site?, path? }` with `problem` from a closed vocabulary; a `CandidateRef` without a string `revisionKey` is now `INVALID_DESCRIPTOR`.
- S8 `MISSING_IMPLEMENTATION` keeps its code; its six sites produce three shapes with every field required: `{ binding, implementation, version, available }`, `{ contract, site }`, `{ contract, implementation, version, available }`. The unknown-family site gains `available: []`; the `set.load()` site (a `CandidateRef` of another Runtime whose slot ids coincide) reports the family and version parsed from the key and the versions the collection holds instead of `{ revision }` with a possibly undefined value; a `CandidateRef` whose `revisionKey` is not `family@version` is `INVALID_DESCRIPTOR`.
- S10 `asSynaError()` (core-internal, not exported) wraps every non-`SynaError` value: `details` is the site's details plus a fixed `cause: { name, message }` record and the original value is `cause` whatever its type; nothing else is read from the foreign value. A `SynaError` passes through unchanged.
