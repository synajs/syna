# Deferred (v0.8)

Things noticed during the v0.6 API consolidation, the v0.7 round, the v0.8 rename and the 1.0.0-rc.1 preparation that were **not** changed, because they are outside the change list of the task book (命名) or because they would change behaviour (语义). Each entry says what was seen and where; none is a commitment, and none is on the frozen surface (`docs/API_STABILITY.md`): a name of the 命名（2.0） section can change only in a major, with the codemod of that major. The items earlier rounds resolved — S1 (waiter deadline), S2 (`env.state` and the ledger), S6 (`FRESH_CONSTRAINT_FAILED` split), S7 (`INVALID_ENV_STATE` / `INVALID_DESCRIPTOR`), S8 (`MISSING_IMPLEMENTATION` shapes), S10 (`asSynaError()`), N2 (the selector remnants) in 0.7, and N1 in 0.8 (the two reference kinds of an implementation record now have two names, `implementationRef` and `candidateRef`; `docs/MIGRATION_V07_TO_V08.md` F6 / F7) — are removed from this list; the numbering keeps its gaps.

## 语义 — behaviour that looked wrong or improvable, left unchanged

| # | Where | Observation | Not done because |
|---|---|---|---|
| S3 | `provides: [primary(C)]` | A default-implementation declaration (the `@Primary` counterpart) would remove most `MISSING_AUTO_POLICY` cases. | 0.6 task book §3.6: no default implementations; the 0.7 and 0.8 task books name `primary()` among the things not to do (a new public name outside their change lists). Still deferred: `MISSING_AUTO_POLICY` with an explicit `auto()` policy is the documented answer, and a default that a package declares for itself would let a dependency choose its supplier without the world saying so. |
| S4 | `C.all` coexistence | Every candidate is a real node of the current Env; a candidate whose setup fails still fails the collection's caller. | 0.6 task book §3.6; the 0.7 and 0.8 task books name the relaxation among the things not to do. Still deferred: a candidate that is not a real node would reintroduce the selector's pre-check (`availability`), whose last remnants 0.7 removed; failing the caller is the honest outcome of "every candidate is part of the topology". |
| S5 | New dependency forms, Entry capabilities, Runtime options | Including `ServiceFamily.range()` (Phase A finding F2 of 0.6): `serviceRange(revision, range)` took a **revision** as the range's origin; a Family-level `range()` would be a range without an origin and would change private-realm resolution (0.5 third round C1/C2). Also `load({ timeoutMs })`: a per-call wait shorter than `loadTimeoutMs`. | 0.6 task book §3.6; D4 deleted `serviceRange` and added nothing; the 0.7 and 0.8 task books name `ServiceFamily.range()` and `load({ timeoutMs })` among the things not to do. Still deferred: S1 made the load timeout the waiter's, so `load({ signal: AbortSignal.timeout(ms) })` already is the shorter wait (`LOAD_CANCELLED`) without a second option for the same thing (naming guideline 4); a Family-level range still has no origin. |
| S9 | `C.all` version resolution with several active revisions | With both `1.2.0` and `1.9.0` of a family active in one Env, `set.resolve({ range: '^1.0.0' })` picks the highest satisfying version (`1.9.0`); the deleted selector picked the active-ancestor revision (`1.2.0`) because only one was active in its world. | This is `C.all`'s existing rule (v0.5 `defaultRuntimePolicy`), recorded in the 0.6 migration table under D3; not a change made in 0.6, 0.7 or 0.8 (the planning layer is unchanged by construction: reference planner differential and the 0.5 snapshots). |
| S11 | Cross-ancestor reuse | Ordinary reuse targets only the parent's currently visible slots (v0.5 §3); a slot an ancestor owned and the parent no longer sees is not searched for (Binding flip-back creates a new instance). | The 0.7 and 0.8 task books name it among the things not to do. Still deferred: 0.5 withdrew the historical-instance search deliberately (`docs/SEMANTIC_CHANGES_V05.md` §3, §9); the lineage pin is the one persistent promise, and a wider search would change plans the snapshots pin. |
| S12 | Prepared / activation groups / any setup barrier | A way to enter an Entry before its owner is `ready`, or to make un-awaited `load()`s hold a setup, keeps being asked for by callers who want a "prepared" world. | The 0.7 and 0.8 task books name Prepared and any barrier among the things not to do. Still deferred: 0.5 withdrew the activation transaction and the completion barrier (`docs/SEMANTIC_CHANGES_V05.md` §2); `OWNER_NOT_READY` and plain Promises are the model (K02/K07), and 0.7's S1/S2 rest on `load()` having no hidden obligation. |
| S13 | A generation-switching host (Runtime hot reload) | A host that swaps a Runtime generation under live Envs, migrating or draining them, would let a long-running process take new definitions without a restart. | The 0.7 and 0.8 task books name it among the things not to do. Still deferred: a Runtime is finite, closed and immutable (v0 core); generation switching is a host concern above it (the site manager of the reference application `apps/multitenant-blog` rotates SiteEnvs by configuration revision inside one Runtime), and nothing on the frozen surface is needed for it. |

## 1.0.0-rc.4 — found while fixing the cleanup phase, left alone

| # | Where | Observation | Left because |
|---|---|---|---|
| S14 | `materializer.ts` `settleSlot()`, the second branch (`slot.unsettledAttempt` after the sequence settled inside the grace) | Defensive and, as the code stands, unreachable: `slot.unsettledAttempt` is set only in the abandoned branch of `runAttemptRaw`, which only `settleSlot`'s *first* branch can trigger — and that branch returns. Every attempt that reaches `closeUnsettled()` therefore has `reportsToClose === false`, so the late close of an abandoned attempt can never report to a `dispose()`. | That is exactly what §13 says should happen ("what the close stopped waiting for reports through an event instead, since the `dispose()` that would have carried it has returned by definition"), so nothing is wrong; removing the branch is a refactor of the close path and rc.4 does not refactor `materializer.ts` (rc.5). Recorded so that the next reader does not mistake it for a live path. |
| S15 | `apps/multitenant-blog`: the second await of `create()`, `context.load()` | A4's acceptance asks for each of the three awaits inside `create()` to be gated once. The first (`boundSites.enter()`) and the third (`auth.load()`) can be gated from a test through the bound authenticator; the second cannot — the site context's only slow dependencies are shared root slots that are already materialized by the time the first site is created, and the application exposes no override hook. | The deadline wraps the whole `record.creation`, so the position is covered by construction and is bracketed by the two positions that are gated. Adding a seam only for the test would be a public change to the application for no other reader. `apps/multitenant-blog/tests/rc4-acquire-deadline.test.mjs` says so in its header. |
| S16 | A `load()` still waiting on a slot whose Env has finished closing | While a waiter is armed, it keeps its slot reachable through the sequence Promise; before rc.4 that reached the Env through `slot.ownerEnv`. rc.4 clears `slot.ownerEnv` when the bounded close completes, so the Env is collectable, but the *slot* stays until the waiter's own deadline (up to `loadTimeoutMs`, 30 s by default) or until the sequence settles. | Ending every waiter at the close would be a new promise ("a close ends the waits of the slots it abandons") that §11 and §13 do not make, and rc.4 clarifies those sections rather than extending them. The Env, its plan and its Input payloads are already released, which is what §13 promises; what remains is one slot and the cleanup closures the user's own `setup()` captured. |
