# `@syna/core` API stability (v0.8)

This document declares the public surface of `@syna/core` frozen from 0.8.0, says what was and was not promised before it, how the surface may change from 1.0 on, and the naming rules every later addition must follow. It is the reference for `docs/MIGRATION_V07_TO_V08.md` (the last rename, item by item, with its codemod), `docs/MIGRATION_V06_TO_V07.md` and `docs/MIGRATION_V05_TO_V06.md` (the earlier lines), `docs/SEMANTIC_CHANGES_V07.md` (the last semantic revision), `docs/GLOSSARY.md` (the vocabulary) and `docs/DEFERRED.md` (what was deliberately not changed, and the names that can change only in a major).

## The declaration (冻结声明)

1. **Before 1.0 no compatibility is promised** (1.0 前不承诺兼容). The 0.x line changed public names in every minor — 0.6 consolidated the API behind one-minor aliases, 0.7 removed those aliases and revised two semantics, 0.8 renamed once more — and each change shipped with a migration document; none of them broke a promise, because none had been made. 0.8.0 is the **last rename before 1.0** (最后一次改名): no name of the public surface changes again before 1.0, under any policy.
2. **The public surface is frozen from 0.8.0** (公开面自 0.8.0 冻结). The frozen surface is the public API `scripts/api-inventory.mjs` records (`work/v08/API_INVENTORY_AFTER.json`: 374 items, 0 `@deprecated`, asserted by the release gate and by `scripts/tests/api-inventory.test.mjs`), with the 26 error codes and the `details` shapes of `docs/API_REFERENCE.md`, every `RuntimeEvent.type` with its payload, `EnvState`, `SlotState`, the `limits` defaults (30_000 / 2_000 / 10_000 / 512), the one serialized shape of `ImplementationRef`, and the semantics of `docs/SEMANTIC_MODEL.md`. From 0.8.0 on — in every 0.8.x and in 1.0 — no rename, no alias, no removal, no re-typing, no changed default and no semantic change. 1.0 publishes this surface as it is.
3. **From 1.0 the surface changes only with a major** (1.0 起只按 major 变化). A change to a public name or to a semantic of the frozen surface happens in a major version and nowhere else. It ships with a migration document and a codemod like `scripts/codemod-v08.mjs`, and it never introduces an alias or a compatibility read path: the one-minor deprecation policy of the 0.6 line (`@deprecated` for one minor, removed in the next) is retired with the rename it served — there is no deprecation minor between 0.8.0 and 1.0 and none after 1.0, and `scripts/tests/deprecations.test.mjs` keeps the register at zero. A minor may still **add** a name under the naming guidelines below; an addition never changes an existing name, type, default or semantic.

Not on the frozen surface, and therefore not promised in either direction: everything `docs/DEFERRED.md` lists — the semantics it defers (`C.all` coexistence relaxation, `primary()`, `ServiceFamily.range()`, `load({ timeoutMs })`, cross-ancestor reuse, Prepared / activation groups, a generation-switching host) and the names its 命名（2.0） section records as candidates for the next major. An addition of that kind is a new name under the naming guidelines, never a change of this surface.

### Registered exception — 1.0.0-rc.3（rc.3 登记例外）

One increment to the frozen surface, and one revision of a frozen semantic, both from the independent audit of 1.0.0-rc.2 (`docs/SEMANTIC_CHANGES_RC3.md`, `work/rc3/BASELINE.md`):

| item | change |
|---|---|
| `RuntimeEvent` | `attempt-abandoned.phase` gains `'cleanup'`: `'setup' \| 'rollback'` → `'setup' \| 'rollback' \| 'cleanup'` |
| `RuntimeLimits` | the doc of `disposalGraceMs`: the limit now also bounds the cleanup phase of each Ready slot |
| `UnsettledAttemptInspection` | the doc of `state`: `abandoned` now also covers a cleanup the close stopped waiting for (no new value) |

`api-inventory` diff against the 1.0.0-rc.2 record: **0 added, 0 removed, 3 changed** — nothing else, asserted by the release gate. The revised semantic is `docs/SEMANTIC_MODEL.md` §13: the disposal grace bounds each Ready slot's cleanup phase as it bounds each attempt, independent SCCs are destroyed concurrently, and every cleanup failure the close waited for reaches `dispose()` exactly once. It is registered here rather than deferred to a major because §13 has said since 0.7 that the close is bounded and that `disposalGraceMs` is what bounds it: rc.2's implementation did not deliver that for cleanups, and a close that can hang forever is not the frozen semantic under another reading — it is the absence of it. The discriminator is the smallest thing that lets the report stay true (the alternative, a fourth `UnsettledAttemptInspection.state`, was not taken).

### No exception — 1.0.0-rc.4（rc.4：零增量）

The round after it, driven by a three-party cross-review (`docs/SEMANTIC_CHANGES_RC4.md`, `work/rc4/BASELINE.md`), needed **no** exception at all and is recorded here for that reason. `api-inventory` diff against the 1.0.0-rc.3 record: **0 added, 0 removed, 0 changed, 0 doc-only** — asserted by the release gate. Six defects of the closing path and of the reference application were fixed inside the frozen surface: the close set is closed before any abort listener runs and the Promise of a close is published before the close begins (N2/N3), a cleanup phase reports the failures it had already determined when the close stopped waiting for it (N1), nothing suspended on a cleanup keeps a closed Env alive any more (N4), a waiter is bounded until the current attempt *ends* rather than until its setup Promise settles (N5), and the acquire deadline of the reference application covers the site creation (A4). `docs/SEMANTIC_MODEL.md` §11 and §13 were **clarified**, not revised: the four clarifications of `docs/SEMANTIC_CHANGES_RC4.md` §2 say more precisely what the sections already promised. No new event type, field, option, error code or discriminator value was added, and none was needed.

### No exception — 1.0.0-rc.5（rc.5：零增量）

The round after that changed no production behaviour at all, so there is nothing to register: `api-inventory` diff against the 1.0.0-rc.4 record is **0 added, 0 removed, 0 changed, 0 doc-only**, and against the 0.8.0 record it is still exactly rc.3's three items above — asserted by the release gate as two separate checks. What the round did change is the suite that guards this surface (two wrong implementations the rc.4 tests could not tell from the right one are now rejected, `docs/SEMANTIC_CHANGES_RC5.md` §2) and where the implementation of the materialization path lives (`materializer.ts` split into the five concerns it orchestrates, with no test changed). `docs/SEMANTIC_MODEL.md` §11 was **clarified** — the two moments of an eager activation stated separately, and a wait ended during a rollback stated not to make an attempt overdue — which is what the implementation has done since rc.4.

The way an unknown or renamed option is refused is a diagnostic, not part of the frozen surface（未知或已改名选项的拒绝方式属于诊断，不属于冻结面）: that no expired or unknown form is read silently is a rule of this document, but which error a refused call receives — the `TypeError`s and the `INVALID_DESCRIPTOR` refusals of `docs/MIGRATION_V07_TO_V08.md` — with its message and its `details` is a diagnostic that a minor may sharpen.

## Persisted data

`ImplementationRef` has exactly one serialized shape, `{ kind: 'implementation-ref', contractId, familyId, range }` (`docs/API_REFERENCE.md`; `docs/MIGRATION_V07_TO_V08.md` §6). That shape is frozen with the API: `Binding.to()` and `parse()` write it, `parse()` and every Runtime read path accept it and nothing else (`INVALID_DESCRIPTOR` with `details.problem` `not-an-object`, `wrong-kind` or `malformed-implementation-ref`). No form an earlier line wrote is read; a stored document written before 0.8 is rewritten before it is read again. `kind` is the on-disk discriminator: it does not change before a major, and a major that changes it changes it with a codemod for stored documents, not with a second read path.

## Naming guidelines

For every API added after 0.8.0:

1. **Descriptors are nouns.** `Contract`, `Input`, `Binding`, `Entry`, `Env`, `ServiceRevision`, `ServiceFamily`, `ImplementationRef`, `CandidateRef`, `ImplementationRecord`, `AnchoredEntry`: a descriptor names a thing, never an action, and carries no suffix that says it is one (`docs/GLOSSARY.md`).
2. **A verb's cost is visible in its name.** `load` may trigger a setup (and therefore wait, fail and retry); `read` never does anything but return the payload; `enter` creates a world; `check` and `explain` never create one; `derive` creates a child world. Do not add a verb whose cost the reader cannot tell from the name, and do not reuse one of these verbs for a different cost.
3. **No internal terms on the call surface.** Slots, realms, the internal meaning of lineage pins and materialization stay in `internal/` and in `inspect()` output, not in method or option names. `anchor` is the one public exception: the Env an `AnchoredEntry` is anchored at is a user-facing concept — and it is not `pinned`, the word of lineage uniqueness.
4. **One name per concept, one concept per name.** A concept with two names is a defect; the second name is removed, not aliased. A name with two meanings is a defect too: `inherited` is what an Input or Binding declaration does, `reused` is what a Service slot is; `range` is what a reference asks for, `version` what a revision has.
5. **Rare options may be verbose; hot paths must be the shortest.** `limits.loadTimeoutMs` and `reuse: { fresh: [...] }` are read rarely; `load()`, `read()`, `enter()`, `run()` and `env.deps` are typed on every call.
6. **Do not collide with Syna's own vocabulary or with the industry's**: a new name may not share its root with `Binding`, `Service`, `Input`, `Entry`, `Env`, `Runtime` unless it names that thing, and may not carry a meaning the industry attaches to a different thing (`scope`, `lease`, `selector`, `session`, `handle`, `descriptor` for a value that is not one).
7. **A report is named for what it reports, not for what it decides.** `LOAD_TIMEOUT` is the waiter's report, not a verdict on the Service; an event is named `<subject>-<what happened>` (`attempt-succeeded-late`, `runtime-attempts-outstanding`), never for a mechanism.

Prohibited by this document: an alias for any name; a compatibility read path for a serialized form; a rename or a semantic change outside a major; a deprecation minor; a third name between an old and a new one.
