# validation/

Machine-readable results produced by the acceptance orchestrator: `node scripts/verify-release.mjs` from 1.0.0-rc.1 on, which reads the workspace version from `package.json` and writes to the directory that version's release profile names (`scripts/release-profiles/<version>.json`, `constants.validation`); the releases whose profile names none write under `v<version>-<mode>/`, which is what the workspace version composed on its own through 1.0.0-rc.5. The 0.8 runs under `v0.8-*` were produced by `scripts/verify-v08.mjs`, the 0.7 runs under `v0.7-*` by `scripts/verify-v07.mjs`, the 0.6 runs under `v0.6-*` by `scripts/verify-v06.mjs`, the 0.5 runs under `v0.5-*` by `scripts/verify-v05.mjs`.

## Two lineages

**`v<version>-<mode>/` at the top level are this repository's own validation rounds.** Each is one gate run of the workspace at the workspace version of its day: `v0.5-dev` … `v1.0.0-rc.6-release`. Most of them — the whole `v1.0.0-rc.1-release` … `v1.0.0-rc.5-release` series — were run while the runtime was still developed under a temporary package identity that this project cannot publish under (`docs/HISTORY.md`, `CHANGELOG.md`). They are **immutable historical evidence**: never deleted, renamed, moved, renumbered or rewritten. Later profiles, the inventory chain and the benchmark baselines cite them by path, and a record whose path or content moves under a citation is no longer a record.

**`public/syna-v<package version>-release/` is the evidence of a release published to npm.** The first is `public/syna-v1.0.0-rc.1-release/`, the gate run behind `syna@1.0.0-rc.1` and `@synajs/tsconfig@1.0.0-rc.1`; the next public candidates are `public/syna-v1.0.0-rc.2-release/`, `public/syna-v1.0.0-rc.3-release/`, and so on. A public run's directory carries exactly what a top-level release run carries — the same manifest, the same steps, the same artefacts, described below.

**The two numbers are not the same number and are not meant to converge.** The workspace version is a private counter of gate rounds; it is what `package.json` says, what names the source archive and what selects the release profile. The package version is the semver the registry sees, and it restarts at `1.0.0-rc.1` for the public identities because that is the first candidate published under them — while the workspace, on its sixth round of the 1.0 line, is `1.0.0-rc.6`. Reading a public package's evidence out of `v1.0.0-rc.1-release/` would therefore be reading the wrong run: that directory is the first *internal* round of the 1.0 line, from the temporary-identity era. The mapping is written down once, in the release profile of the workspace version (`constants.packages` and `constants.validation`), and the gate asserts the packed tarballs are the packages it declares.

## What a run directory contains

- `v<version>-dev/manifest.json`, `v<version>-dev/logs/*.log` — development gate (G0): every spawned command with exit code, timing, TAP counts and log path; `benchmark-v0.5.json` (the planning workload, unchanged since 0.5, measured without extra V8 flags for the budgets); `benchmark-compare/` (same-session comparison with the 0.8.0 source exported from git, both benchmark processes under `--expose-gc --no-maglev`, ±10 % on p50/p95, plan-cache counters equal) or `benchmark-compare.json` (comparison with the recorded 0.8.0 file when the commit cannot be exported); `api-inventory.md` / `.json` (public API of this source; the gate asserts 0 `@deprecated` items) and `api-inventory-diff.md` (its diff against the 0.8.0 record `v0.8-release/api-inventory.json`, signature changes apart from JSDoc-only changes; the step `api-inventory-frozen` requires the inventory to be identical to that record item by item); `codemod-idempotent.json` (the rename codemod's dry run over the migrated tree: 0 edits, 0 hand sites); `old-reference-tokens.json` (the scan of the core source, tests and type tests for the pre-0.8 reference tokens: 0 hits); `vendor-name-scan.json` and `package-name-scan.json` (the two current-line name scans, each listing what it allowed and why); `working-set.json`.
- `v<version>-release/manifest.json`, `v<version>-release/logs/*.log` — release gate (G0 + G1): additionally the archive scan, archive hashes, the clean-directory rebuild steps (the codemod dry run repeated inside the unpacked archive), package tarballs, the tarball audit `pack-audit.json` (what each packed package is and what it carries), the independent consumer smoke result and `readme-consumer.json` (the project built from the canonical README with the packed runtime tarball as its only dependency: the README's digest, its files, the programs run and what the consumer installed). The same manifest is copied to `RELEASE_MANIFEST.json`; archive and tarball hashes are listed in `v<version>-release/SHA256SUMS.txt` (the hash list of the 0.5 task package, `work/v05/task-package/SHA256SUMS.txt`, is that package's own and is never rewritten).
- `v<version>-release/blog-request-latency.json` — end-to-end multitenant-blog request latency on both backends (report only, rendered in `docs/VALIDATION.md`; not a budget)
- `v<version>-<mode>/working-set.json` — H11/P05 working-set report written by `apps/multitenant-blog/tests/site-manager.test.mjs` for that run (heap samples after GC, records per phase, eviction counts). A plain `npm run test:app` writes it under `work/v05/` instead, so tests never rewrite tracked files.
- `v0.8-release/`, `v0.7-release/`, `v0.6-release/`, `v0.5-dev/`, `v0.5-release/` — the 0.8.0, 0.7.0, 0.6.0 and 0.5.0 runs, kept as the record of those releases; `v0.8-release/api-inventory.json` is the record of the frozen surface (`docs/API_STABILITY.md`).
- `public/syna-v<package version>-release/` — a public release run, with the same contents as a `v<version>-release/` directory above. `manifest.json` records the published identities it gates (`packages`) and its own path (`validation`) beside the workspace version it was run at.

## Hash discipline

The manifest records the **source** fingerprint (sha256 over path + content hashes of every archived source file, excluding `dist`, `node_modules`, the dev validation directories and — from 1.0.0-rc.1 on — `docs/VALIDATION.md`, which `scripts/validation-doc.mjs` generates from the manifest after the run) and the **archive** hashes computed after the archive is written. The manifest itself is never placed inside the archive it describes; it is a sidecar that references the archive hash, and so is `docs/VALIDATION.md`. A release's evidence — `RELEASE_MANIFEST.json`, its `v<version>-release/` directory and the generated `docs/VALIDATION.md` — is committed together with the release from one gate run on the committed source (git provenance clean), so the recorded fingerprint and archive hashes hold on the commit that carries them. Commands are recorded with the workspace root replaced by `<root>`; git provenance is captured before the first step runs. Any source change invalidates the recorded fingerprint and requires a new run.
