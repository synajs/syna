# validation/

Machine-readable results produced by the acceptance orchestrator: `node scripts/verify-release.mjs` from 1.0.0-rc.1 on, which reads the version from `package.json` and writes under `v<version>-<mode>/`; the 0.8 runs under `v0.8-*` were produced by `scripts/verify-v08.mjs`, the 0.7 runs under `v0.7-*` by `scripts/verify-v07.mjs`, the 0.6 runs under `v0.6-*` by `scripts/verify-v06.mjs`, the 0.5 runs under `v0.5-*` by `scripts/verify-v05.mjs`.

- `v<version>-dev/manifest.json`, `v<version>-dev/logs/*.log` — development gate (G0): every spawned command with exit code, timing, TAP counts and log path; `benchmark-v0.5.json` (the planning workload, unchanged since 0.5, measured without extra V8 flags for the budgets); `benchmark-compare/` (same-session comparison with the 0.8.0 source exported from git, both benchmark processes under `--expose-gc --no-maglev`, ±10 % on p50/p95, plan-cache counters equal) or `benchmark-compare.json` (comparison with the recorded 0.8.0 file when the commit cannot be exported); `api-inventory.md` / `.json` (public API of this source; the gate asserts 0 `@deprecated` items) and `api-inventory-diff.md` (its diff against the 0.8.0 record `v0.8-release/api-inventory.json`, signature changes apart from JSDoc-only changes; the step `api-inventory-frozen` requires the inventory to be identical to that record item by item); `codemod-idempotent.json` (the rename codemod's dry run over the migrated tree: 0 edits, 0 hand sites); `old-reference-tokens.json` (the scan of the core source, tests and type tests for the pre-0.8 reference tokens: 0 hits); `vendor-name-scan.json` and `package-name-scan.json` (the two current-line name scans, each listing what it allowed and why); `working-set.json`.
- `v<version>-release/manifest.json`, `v<version>-release/logs/*.log` — release gate (G0 + G1): additionally the archive scan, archive hashes, the clean-directory rebuild steps (the codemod dry run repeated inside the unpacked archive), package tarballs, the tarball audit `pack-audit.json` (what each packed package is and what it carries), the independent consumer smoke result and `readme-consumer.json` (the project built from the canonical README with the packed runtime tarball as its only dependency: the README's digest, its files, the programs run and what the consumer installed). The same manifest is copied to `RELEASE_MANIFEST.json`; archive and tarball hashes are listed in `v<version>-release/SHA256SUMS.txt` (the root `SHA256SUMS.txt` is the task-document hash list shipped with the workspace and is never rewritten).
- `v<version>-release/blog-request-latency.json` — end-to-end multitenant-blog request latency on both backends (report only, rendered in `docs/VALIDATION.md`; not a budget)
- `v<version>-<mode>/working-set.json` — H11/P05 working-set report written by `apps/multitenant-blog/tests/site-manager.test.mjs` for that run (heap samples after GC, records per phase, eviction counts). A plain `npm run test:app` writes it under `work/v05/` instead, so tests never rewrite tracked files.
- `v0.8-release/`, `v0.7-release/`, `v0.6-release/`, `v0.5-dev/`, `v0.5-release/` — the 0.8.0, 0.7.0, 0.6.0 and 0.5.0 runs, kept as the record of those releases; `v0.8-release/api-inventory.json` is the record of the frozen surface (`docs/API_STABILITY.md`).

Hash discipline: the manifest records the **source** fingerprint (sha256 over path + content hashes of every archived source file, excluding `dist`, `node_modules`, the dev validation directories and — from 1.0.0-rc.1 on — `docs/VALIDATION.md`, which `scripts/validation-doc.mjs` generates from the manifest after the run) and the **archive** hashes computed after the archive is written. The manifest itself is never placed inside the archive it describes; it is a sidecar that references the archive hash, and so is `docs/VALIDATION.md`. A release's evidence — `RELEASE_MANIFEST.json`, its `v<version>-release/` directory and the generated `docs/VALIDATION.md` — is committed together with the release from one gate run on the committed source (git provenance clean), so the recorded fingerprint and archive hashes hold on the commit that carries them. Commands are recorded with the workspace root replaced by `<root>`; git provenance is captured before the first step runs. Any source change invalidates the recorded fingerprint and requires a new run.
